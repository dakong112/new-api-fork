## 2. 顶部公告滚动栏

登录后的所有控制台页面，顶栏下方会出现一条公告栏，横向循环滚动**系统公告**的内容。

**怎么发布**：在「系统设置」中编辑「系统公告」（即 `Notice`）并保存。滚动栏和登录后的公告弹窗读取的是同一份内容。

**显示规则**

- 公告支持 Markdown。滚动栏只显示纯文本摘要：粗体、标题、链接等符号会去掉，链接保留文字。
- 点击滚动的文字，会打开右上角铃铛的「系统公告」标签，查看完整的 Markdown 内容。
- 鼠标悬停或键盘聚焦时暂停滚动。系统开启「减少动态效果」时不滚动，只静态显示。
- 滚动速度随文字长度自动调整，一圈最短 15 秒。

**关闭与重新出现**

- 用户点击右侧 ✕ 可以关闭滚动栏，关闭状态保存在用户自己的浏览器里。
- 管理员**修改公告内容**后，滚动栏会重新出现。
- 公告内容为空时，滚动栏不显示，页面布局恢复原样。

> 「控制台内容 → 公告」是另一个功能（公告列表），只显示在铃铛的「公告」标签和概览页面板里，**不会**出现在滚动栏中。

## 3. 顶部联系方式

顶栏中间显示管理员配置的联系方式按钮（例如「QQ交流群 123456」），采用主题色胶囊样式，比较醒目。

**配置**：系统设置 → 控制台内容 → 联系方式。

| 字段 | 说明 | 限制 |
|---|---|---|
| 类型 | QQ、微信、Telegram、Discord、邮箱、链接，决定显示的图标 | 必选 |
| 名称 | 例如「QQ交流群」 | 必填，最多 30 字符 |
| 展示值 | 例如群号 `123456` | 最多 100 字符 |
| 链接 | 例如 `https://qm.qq.com/q/xxxx` 或 `mailto:admin@example.com` | 选填，只允许 `http`、`https`、`mailto` |

「展示值」和「链接」至少要填一个；最多可以添加 10 条。右上角的开关控制整组联系方式是否显示。

**点击行为**

| 配置 | 用户点击后 |
|---|---|
| 填了链接 | 在新标签页打开链接 |
| 没填链接 | 复制展示值，并提示「已复制」 |
| 微信，且填了链接 | 弹出由链接生成的二维码 |

**显示**：桌面端显示「图标 + 名称 + 展示值」；窄屏（平板竖屏、手机）只显示图标，鼠标悬停或长按可以看到完整文字。

**安全**：后端会拒绝 `javascript:` 等危险链接和包含脚本的内容。

## 4. 系统公告弹窗：「今日关闭」只屏蔽当前公告

**之前的问题**：用户点过一次「今日关闭」后，当天发布的**任何**新公告都不会再弹出。

**现在的行为**：「今日关闭」只屏蔽当时那一条公告。管理员发布新内容后，即使是同一天，弹窗也会再次出现。

- 「关闭」：把当前公告标记为已读，以后不再弹出这一条。
- 「今日关闭」：当天不再弹出这一条；第二天或内容变化后会再弹出。

## 5. 渠道页显示分组倍率

渠道管理页的卡片视图和列表视图中，每个分组标签右侧显示该分组的倍率，例如 `default 1x`、`vip 2x`：

- 倍率大于 1 显示橙色，小于 1 显示蓝色。
- 新建、编辑渠道时，分组下拉选项也带倍率，例如 `vip (2x)`。
- 倍率表里没有的分组只显示名称；开启「隐藏敏感信息」时，分组名和倍率一起隐藏。

倍率读取自「分组定价」中配置的分组倍率，管理员可以调用 `GET /api/group/ratios` 获取。

## 6. 备选分组手动排序

位置：系统设置 → 计费与支付 → 分组定价 → **备选分组**。

每个分组一行：

1. 用「添加分组」下拉框选择备选分组。已选的分组和分组自身不会出现在下拉中。
2. 下方的编号列表就是失败后依次尝试的顺序（1 → 2 → 3）。
3. 调整顺序：按住左侧把手上下**拖动**，或点右侧 **↑ / ↓**，也可以在把手获得焦点后用键盘上下方向键。
4. 点右侧 ✕ 移除某个备选分组。
5. 改完点右上角「保存分组设置」。

> 备选分组只对开启了「备选分组重试」的令牌生效。这是令牌编辑页中的开关，`auto` 分组的令牌显示为「跨分组重试」，两者是同一个设置。请求在备选分组中成功时，按该备选分组的倍率计费。

## 7. 分组网络重试（502 / 504 / 524 换渠道重试）

### 7.1 解决什么问题

上游渠道挂在 Cloudflare 等网关后面时，经常出现：

- `502`：上游源站返回无效或不完整的响应（过载、重启、连接被重置）；
- `504` / `524`：网关等待上游超时（Cloudflare 免费版和 Pro 版回源超时固定为 100 秒）。

原来的逻辑中，**504 和 524 一律不重试**：第一个渠道超时就直接把错误返回给用户，即使还有其他可用渠道。502 虽然会重试，但同一优先级里可能反复抽中刚失败的渠道。

### 7.2 开启方式

系统设置 → 计费与支付 → 分组定价 → **定价分组**。分组表格中有一列「网络重试」，每个分组一个开关，按需打开后点「保存分组设置」。默认全部关闭；关闭时行为与原来完全一致。

这个开关**不依赖备选分组**：没有配置备选分组的分组也可以打开，此时只在本分组内换渠道。分组配置了备选分组时，本分组的渠道全部失败后，才会继续转到备选分组。

### 7.3 开启后的行为

某个分组的请求，在该分组的渠道上遇到 502、504 或 524 时：

1. **允许重试**：504 和 524 也会重试；502 不再依赖全局「自动重试状态码」配置。
2. **先在本分组内换渠道**：排除本次请求**已经试过的所有渠道**，在剩下的渠道中选优先级最高的（同一优先级按权重随机），依次尝试。
3. **再进入备选分组**：本分组没有可用渠道后，按「备选分组」中配置的顺序继续尝试。
   - **前提：令牌开启了「备选分组重试」**（`auto` 分组令牌为「跨分组重试」）。未开启时只在本分组内重试，用完即停止。
   - 在备选分组中成功时，按备选分组的倍率计费。
4. **全部失败**：返回给用户的是最后一个上游的真实错误（例如 524 或 502），而不是「无可用渠道」。

**示例**：分组 `default` 有渠道 A（优先级 10）、B（优先级 5）、C（优先级 0），备选分组为 `vip`，令牌开启了「备选分组重试」。

```
A 返回 524 → 换 B（未试过、优先级最高）→ B 返回 502 → 换 C → C 成功 ✓
（若 C 也失败）→ default 已无可用渠道 → 进入 vip 分组 → 成功则按 vip 倍率计费
```

### 7.4 仍然生效的限制

- **总次数**：仍受「系统设置 → 请求策略 → 会话与重试」中「重试次数」的限制。**重试次数为 0 时，这个开关不起作用。**
- **固定渠道**：开启了渠道亲和性「严格会话」或请求被固定到某个渠道时，不会换渠道。
- **异步任务不在范围内**：Midjourney、视频等异步任务的提交仍按原规则处理。

### 7.5 费用与风险

- **用户只计费一次**：每个请求只预扣一次，只按最终成功的那次结算，失败的尝试会退还。
- **上游成本可能重复**：超时（504 / 524）时，上游可能已经执行完并扣了费用，再换渠道执行一次，**站点的上游成本可能会付两次**。502 一般是上游没有正常处理，风险较小。
- **用户等待更久**：一次 524 本身就要等待约 100 秒，再换渠道需要额外时间。建议重试次数设为 3 左右，并引导用户使用流式请求。

### 7.6 在使用日志中查看

使用日志（仅管理员可见）：

- 发生过网络重试的记录，渠道列旁会显示橙色的 **「网络重试」** 标记。
- 点击渠道旁的链路图标，可以看到每一跳的状态码，例如 `#1 (524) → #3 (502) → #7 ✓`。普通重试的链路现在也会带状态码。
- 打开日志详情，「决策记录」中可以看到每次尝试的渠道、分组、状态码和耗时，原因显示为「上游网络错误，改走未尝试的渠道」。

> **全部重试都失败的请求**只有在开启错误日志后才会写入日志，见[第 9 节](#9-上线检查清单)。

## 9. 上线检查清单

**构建顺序**：前端产物会打包进 Go 程序，必须先构建前端：

```bash
cd web && bun install && bun run build && cd ..
go build -o new-api .
```

**上线前**

- [ ] 备份数据库，保留上一版程序，方便回滚。本次没有修改数据库表结构，新配置项存放在现有的系统设置表中。
- [ ] 检查环境变量（见下表）。
- [ ] 检查反向代理超时（见下文）。

**相关环境变量**

| 变量 | 建议值 | 说明 |
|---|---|---|
| `ERROR_LOG_ENABLED` | `true` | **想在日志里看到「全部重试仍失败」的请求，必须开启。** 默认关闭，关闭时失败的请求不写日志。 |
| `RELAY_RESPONSE_HEADER_TIMEOUT` | `120`（默认 1800） | 单次尝试等待上游响应头的最长秒数。超时即判定失败，交给重试逻辑换渠道。只限制等待响应头的时间，不会中断正在输出的流式回复。 |
| `STREAMING_TIMEOUT` | 默认 300 | 流式输出期间超过这个秒数没有数据就断开。 |
| `RELAY_TIMEOUT` | **不建议设置** | 它限制整个响应的读取时间，会截断正常的长流式回复。 |

**后台设置建议**

- 「重试次数」设为 3 左右。网络重试每次都会换新渠道，不需要设得很大。
- 只给确实需要的分组打开「网络重试」开关。
- 希望进入备选分组时，确认对应令牌开启了「备选分组重试」（`auto` 分组令牌为「跨分组重试」）。

**反向代理（以 OpenResty / Nginx 为例）**

开启重试后，一个请求的总耗时等于所有尝试耗时之和。反向代理默认 60 秒的读超时会先于 new-api 断开，导致用户收到 504，而 new-api 还在后台重试。建议：

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;  # 需要在 http 块中配置 map
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_connect_timeout 10s;
    proxy_send_timeout    600s;
    proxy_read_timeout    600s;   # 默认 60s，务必调大
    send_timeout          600s;

    proxy_buffering off;          # 流式输出不要缓冲
    proxy_cache off;
    proxy_request_buffering off;
    client_max_body_size 50m;
}
```

在 `http {}` 块中添加：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

> **注意**：如果站点域名本身也走 Cloudflare 代理（橙色云朵），非流式请求最长只能等待 100 秒，超过后用户会收到站点自己的 524，调大 Nginx 超时也没有用。可以引导用户使用流式请求（`stream: true`），或为 API 单独配置一个不经过 Cloudflare 的子域名。

## 10. 新增配置项与接口

**新增系统设置项**（存放在系统设置表中，均可在后台界面修改）

| 键 | 类型 | 说明 |
|---|---|---|
| `console_setting.contact_links` | JSON 数组 | 联系方式列表，每项为 `{icon, label, value?, url?}` |
| `console_setting.contact_links_enabled` | 布尔 | 是否显示联系方式，默认 `true` |
| `GroupNetworkRetryGroups` | JSON 数组 | 开启了网络重试的分组名，例如 `["default","vip"]`，默认 `[]` |

分组改名时，`GroupNetworkRetryGroups` 中的分组名会一起更新。

**新增或变更的接口**

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /api/group/ratios` | 管理员 | 返回各分组的倍率，例如 `{"default":1,"vip":2}` |
| `GET /api/status` | 公开 | 新增 `contact_links_enabled`；联系方式启用时新增 `contact_links` |

**使用日志字段**（仅管理员可见，位于 `other.admin_info`）

- `use_channel`：本次请求依次尝试过的渠道 ID。
- `request_policy`：每次尝试的决策记录。网络重试的决策为 `{"action":"retry","reason":"network_error_retry","source":"group"}`，失败记录中带上游状态码 `status`。
